# First contact: install, first run, uninstall on the clean VM (E2, E10, E3)

5 September 2026. The first time DR Companion has been installed on a machine
that did not build it.

Everything below was observed. Where something was **not** observed, it says so
rather than being filled in from what the code does. Screenshots are the
`first-run-2026-09-05-NN-*.png` files beside this document, numbered in the
order the prompts appeared.

| | |
|---|---|
| Machine | `drc-clean-win11`, restored from snapshot `clean` before anything was done |
| Guest | Windows 11 Enterprise LTSC Evaluation, **10.0.26100.1742** |
| Account | `tester`, a **local Administrator**, auto-logged-in |
| Artefact | `DR Companion_0.1.1_x64-setup.exe`, 217,297,383 bytes |
| SHA-256 | `1f813b6f74982f9e2a6e39095f37a59526137f1e838033f1e59d6f97810be09e` |
| Screen | 1024x768 for the install and the app's first paint; raised to 1440x900 partway through, for the reason in "Defect 1" |

The SHA-256 in that table was measured **inside the guest** on the file that
actually arrived (`certutil -hashfile`), not copied from the build record. It
matches the figure in `vm.md` exactly, so the thing installed here is the thing
that was built.

## The blocker in `vm.md` was misdiagnosed, and guest control works

`vm.md` and E2's `blocked-on:` both say `VBoxManage guestcontrol` never becomes
ready on this VM — "the guest execution service is not ready (yet)", four
attempts across two boots. That is not what is wrong, and the whole of this
increment ran through guest control.

Two things were true at once and only one of them was recorded:

1. **The earlier attempts were made before anyone had logged in.** Guest
   Additions reports `GuestAdditionsRunLevel=2` at the sign-in screen and `3`
   once the desktop is up. The execution service belongs to run level 3. The
   VM auto-logs in, so waiting about a minute after `startvm` is the entire
   fix.
2. **Nobody had the password**, so even at run level 3 the next error would
   have looked like another failure. It is in the VM's own unattended answer
   file, which is still on disk:

   ```
   C:\Users\Admin\VirtualBox VMs\drc-clean-win11\Unattended-*-autounattend.xml
   ```

   `tester` / `drc-test-vm`, in `<AutoLogon>` and `<LocalAccounts>`.

With those two, this works and is the route to use:

```bash
VB="C:/Program Files/Oracle/VirtualBox/VBoxManage.exe"
"$VB" snapshot drc-clean-win11 restore clean
"$VB" startvm drc-clean-win11 --type gui
sleep 60   # wait for RunLevel 3 - check it, do not assume:
"$VB" showvminfo drc-clean-win11 --machinereadable | grep GuestAdditionsRunLevel
"$VB" guestcontrol drc-clean-win11 --username tester --password drc-test-vm \
      copyto <hostfile> --target-directory "C:/Users/tester/drc/"
```

Three mechanics that cost time and are not obvious:

- **`--target-directory` needs a trailing slash.** Without one,
  `copyto ... --target-directory "C:/Users/tester/drc"` fails with
  *"Destination ... already exists and is a directory"*.
- **Passing arguments to `cmd.exe` through `guestcontrol run` did not work**
  in any form tried. Write a `.cmd` file, `copyto` it, and run it with no
  arguments. (`.cmd` files need CRLF — `sed -i 's/$/\r/'`.)
- **Git Bash rewrites `/c` into `C:/`** before VBoxManage sees it. Export
  `MSYS_NO_PATHCONV=1`, or avoid switches that look like paths.

For anything the GUI has to do, `controlvm screenshotpng` reads the screen and
`controlvm keyboardputscancode` types, both with no guest cooperation at all.
Mouse clicks were done from inside the guest with `SetCursorPos` + `mouse_event`
through a copied-in PowerShell file; a process started by guest control does
land in the interactive session, which is what makes that work.

`vm.md` has been corrected. The in-guest build number it records as unverified
is now measured: `ver` inside the guest says `10.0.26100.1742`, agreeing with
what VirtualBox read off the ISO.

## Delivery: downloaded, not copied, and that is the point

The installer was served from the host over HTTP and fetched **with Microsoft
Edge inside the guest**, because that is what decides whether SmartScreen ever
appears. A file pushed in with `guestcontrol copyto` carries no Mark of the
Web, so it would have installed with no security prompt at all and the run
would have proved nothing about what a stranger sees.

The downloaded file carried a real zone marker, confirmed on the file itself:

```
> Get-Content ... -Stream Zone.Identifier
[ZoneTransfer]
ZoneId=3
HostUrl=http://10.0.2.2:8731/DR%20Companion_0.1.1_x64-setup.exe
```

`ZoneId=3` is "Internet". This is the same state a GitHub release download
arrives in, so the prompts below are the prompts a real user gets.

to let an unsigned binary through, and four are the installer.

| 2 | Edge, downloads flyout | overflow menu: Delete / **Keep** / Report this file as safe / Learn more | Hover the item, open `...`, choose Keep | 03 |
| 3 | Microsoft Defender SmartScreen | "Microsoft Defender SmartScreen couldn't verify if this file is safe because it isn't commonly downloaded... **Publisher: Unknown**" | Buttons are **Delete** (default, highlighted) and Cancel. Keeping the file is behind **Show more → Keep anyway** | 04, 05 |
| 4 | NSIS | "Welcome to DR Companion Setup" | Next | 06 |
| 5 | NSIS | "Choose Install Location" — `C:\Users\tester\AppData\Local\DR Companion`, "Space required: 210.8 MB" | Next | 07 |

| 7 | NSIS | "Installation Complete" then "Completing DR Companion Setup", with **Run DR Companion** and **Create desktop shortcut** both ticked | Finish | 09, 10 |

**Administrator elevation: never requested.** No UAC prompt appeared at any
point — not for DR Companion's installer, not for Ruby4Lich5's installer
underneath it, and not for the uninstaller. The install is per-user into
`%LOCALAPPDATA%`, and Ruby4Lich5 writes `C:\Ruby4Lich5` under the default ACL
that lets an authenticated user create folders at the root of `C:`. Worth
saying plainly because it is a genuine advantage and it is the kind of claim
that is usually assumed rather than checked: **a user with no administrator
rights can install this**, and this run is evidence for that only on an
account which happened to have them — see "What was not tested".

There is **no licence page anywhere in the installer**, despite the payload
bundling Ruby4Lich5 and Lich (BSD-3). The licence is shown inside the app
(E9) and by Ruby4Lich5's own installer, not by this one.

## E10 — the wizard, step by step

The app launches itself from the installer's last page. Its first screen is
**"Missing pieces — 0 of 3 ready"** (shot 11).

Total elapsed, from pressing Enter on the downloaded installer to the app
logging **"All dependencies found. Connecting."**: **11 minutes 15 seconds**
(13:28:26Z to 13:39:41Z).

That figure is honest but it is not a human's pace, and the difference matters
if anyone is tempted to quote it. It is wall-clock for an automated operator
that took a screenshot and decided what to do between every click, so it
contains idle time a person would not spend. The parts that are the machine's
and not the operator's:

| Segment | Time | Whose |
|---|---|---|
| NSIS extraction of 217 MB | ~45 s | machine |
| Ruby4Lich5's own installer, start to Finish | 3 m 48 s | machine |
| Bridge script install | < 2 s | machine |
| everything else | ~6 m | operator latency + reading |

So the floor for a person who knows what they are doing is **under five
minutes**, nearly all of it waiting for two extractions.

### Step 1 — Ruby runtime

Shown as: "Not on your PATH, and not in any of the usual folders", offering
"Ruby4Lich5 — included with this app *(suggested)* — Already here, installs
with no download", v5.20.1, 65.4 MB.

Clicking **Install** did not install anything; it extracted and verified the
bundled copy, then changed the buttons to **Run the installer** / **Show me the
file** and said so: *"Verified and saved. It has not been run. Opening it
starts that project's own installer, which asks its own questions."* The app's
log records the check: `Verified the bundled copy: sha256 2b0f90533eda7e37...`
(shots 12, 13).

That two-stage design is right and the wording is honest. It also means the
bundled Ruby is real, not the stub — E1's claim about `--require-real` holds up
on the delivered artefact.

**Did a program need me here?** No, for the extract-and-verify half. Yes, for
what comes next.

### Step 2 — Ruby4Lich5's own installer (a third-party wizard)

Four more pages, none of them DR Companion's (shots 14-18):

1. "Select Destination Location" — `C:\Ruby4Lich5`
2. "Select Components" — a dropdown defaulting to **"Both Lich and Ruby"**
3. **"Select Additional Tasks — Lich5 Folder Location"** — see Defect 2
4. "Installing", then "Completing the Ruby4Lich5 Setup Wizard", with an
   unticked "Install Ruby DevKit (developers — downloads MSYS2, needs network)"

**Did a program need me here?** **Yes, unavoidably.** This is a foreign
installer with its own choices, and DR Companion cannot answer them. The app
warns that it "asks its own questions", which is accurate, but it offers no
guidance on what to answer — and one of the answers is a real fork in the road.

### Step 3 — Companion bridge script

After **Check again**, the wizard read "2 of 3 ready" with Ruby and Lich both
**Found** (shot 19), and a new row appeared: "Companion bridge script — Ready
to install… This one is ours: a single Ruby file copied into Lich's scripts
folder. Nothing is downloaded, and it is the only thing this app installs for
you."

One click. Installed to
`C:\Users\tester\Desktop\Lich5\scripts\companion_bridge.lic`, 131,142 bytes,
in under two seconds.

**Did a program need me here?** No. One click, no input, no choices.

### Steps that appeared but were not required

Once Lich was found the wizard grew three optional rows: **Game frontend
(Genie)** (not found, marked Optional), **DragonRealms script suite** (222
scripts, 2.6 MB, "each file is checked against the git blob hash GitHub
publishes before anything is written, and one mismatch aborts the whole
install") and **Map database**. None was needed to reach a running app and
none was exercised in this run.

### Could a stranger finish it unaided?

**Yes** — with one qualification, Defect 2 below. The prose throughout is
plain, it says what will happen before it happens, and it distinguishes what
the app does from what a third party's installer does. Nothing asked for a
credential, an account, a path, a port, or anything a person would have to go
and find out. That is a genuinely good result and it is the thing E10 exists
to ask.

## Defects found

### Defect 1 — the window opens larger than the screen and is not clamped

On the 1024x768 display the app's own first-run window opened at **1196 x 859
at position (52, 0)**, measured with `GetWindowRect`, not estimated from the
picture:

```
SCREEN=1024x768
WIN 'DR Companion' proc=dr-companion L=52 T=0 R=1248 B=859 W=1196 H=859
```

224 px of it is off the right edge of the display and 91 px below the bottom.
The controls that fall off include **"Check again"** and **"App folder"** in the
setup wizard's header — that is, the wizard's own re-scan button is
unreachable on a small screen (shot 11 is the evidence; shot 12 is the same
screen after the display was raised to 1440x900 to continue).

The window is not maximised, cannot be dragged left far enough to recover the
right edge without also losing the left, and Windows did not shrink it to the
work area. 1024x768 is small, but the failure is that the size is not clamped
to the display at all, so the same thing happens on any screen shorter or
narrower than the default the app asks for.

The rest of this walkthrough was done at 1440x900. Everything before shot 12 is
at the original resolution.

### Defect 2 — the Ruby4Lich5 default is the GemStone IV layout

Ruby4Lich5's "Select Additional Tasks" page (shot 16) offers:

- **(•) Place in Desktop (`C:\Users\tester\Desktop\Lich5`) — preferred for Gemstone IV**  ← the default
- ( ) Place in Ruby4Lich5 (`C:\Ruby4Lich5\Lich5`) — preferred for DragonRealms

DR Companion is a DragonRealms client, and the default on the page it sends
users to is the **other game's** layout. A person clicking Next through the
defaults, which is what most people do, gets the arrangement the page itself
labels as not theirs.

**This run deliberately took the default**, to find out what actually happens
rather than to predict it.

**What actually happened: it worked.** DR Companion found Lich at
`C:\Users\tester\Desktop\Lich5` and reported it **Found**, and the bridge
script installed into that tree correctly. Detection is not hardcoded to
`C:\Ruby4Lich5`, which is a better result than the repository's own habit of
writing that path everywhere would suggest.

So this is a **wording and guidance defect, not a breakage**: the severity is
"a user is told, by a page we send them to, that they are probably choosing
wrong", plus whatever confusion follows from having Lich in a place none of
this project's documentation mentions. One sentence in the Ruby row — *"either
option works; the DragonRealms one keeps everything together"* — closes it.
Filed here rather than fixed, because it is not this increment's file to touch.

### Defect 3 — the first screen after setup is full of fabricated game state

With setup complete the app goes straight to the main UI (shot 20) showing
**"In combat, 84 of 100 health"**, a character called **"Dan the Bold"**, room
308 in the Empaths' Guild, eighteen other people present, a full stat block and
a populated skills list. On a machine that has never connected to anything.

It is labelled — there is a `MOCK` badge by the character name, a "Mock"
indicator top right, and the command box reads "Not attached" — so this is not
dishonest. But a first-time user's first sight of the product is a screen of
invented numbers, and the labels are small relative to the fiction. Worth a
decision rather than an accident: either an empty state, or the mock data made
obviously synthetic.

### Defect 4 — publisher reads as "github"

Settings → Apps lists the app as **"DR Companion / 0.1.1 / github / 211 MB"**
(shot 21). The publisher field is the literal string `github`. Whatever the
right value is, it is not that.

### Defect 5 — a failed load on the first screen, unexplained

Bottom bar of shot 20: `Hmv-da1480-ola1015 — unavaila...` with a **Retry**
button, on a first run that had just reported everything found. What that
identifier is and what failed was **not established** — it is recorded here as
an observation, not diagnosed, because chasing it was outside this increment.

## E3 — uninstall through Settings → Apps

Settings → Apps → Installed apps → DR Companion → `...` → Uninstall →
"This app and its related info will be uninstalled" → Uninstall.

That hands over to the app's own NSIS uninstaller (shots 22, 23), which shows
one page:

> Uninstalling from: `C:\Users\tester\AppData\Local\DR Companion\`
> ☐ **Delete the application data**

**The checkbox is unticked by default**, which is the correct default and is
exactly the behaviour this increment was written to check. It was left unticked
here, because that is what a person clicking through gets. "Uninstallation
Complete" (shot 24). No elevation prompt. Roughly four minutes end to end,
almost all of it operator latency; the uninstall itself took about 20 seconds.

Both lists below come from the same script run before and after
(`inv.ps1`, reproduced in the appendix), so they are comparable line for line.

### Still there after uninstall — user data, and two things that are not

| What | Size | Should it survive? |
|---|---|---|
| `%LOCALAPPDATA%\io.github.dancockrell.dr-companion\` — the WebView2 profile, including `EBWebView\Default\Local Storage\leveldb` where the app's settings live | 302 files, 46,868,004 bytes | **Yes.** This is the user data. Correct. |
| `%LOCALAPPDATA%\DR Companion Data\downloads\Ruby4Lich5.exe` | 65 MB | **No.** A cached copy of the bundled installer. Not user data, and 65 MB of it. |
| `%LOCALAPPDATA%\DR Companion Data\presentation-bridge.port`, `presentation-bridge.token`, `script-api.port`, `script-api.token` | 4 files | **No.** Live bearer tokens for the local bridges, left on disk after the thing that used them is gone. |

`%APPDATA%` (roaming) **never had a DR Companion entry at all**, before or
after — its top level is `Adobe` and `Microsoft` on this machine and nothing
else. So the answer to E3's "list what remains under `%APPDATA%`" is: nothing,
because nothing was ever put there. Everything the app writes is under
`%LOCALAPPDATA%`.

The two rows marked **No** are the finding. Leaving the port and token files is
the one worth acting on: they are credentials for a local socket, and an
uninstall is precisely when they stop having an owner.

## What was not tested

Stated so nobody reads a gap as a pass:

- **A non-administrator account.** `tester` is a local Administrator. The run
  never raised UAC, which is consistent with the install being per-user, but
  whether a standard user can create `C:\Ruby4Lich5` was not established here.
- **The uninstaller's "Delete the application data" path.** Only the default
  (unticked) was exercised.
- **Any real game connection.** Nothing here touched DragonRealms; the app was
  in mock mode throughout, and the "Connecting" line in its log was not
  followed to a connection.
- **The optional wizard rows** — Genie, the 222-script DragonRealms suite, the
  map database.
- **A GitHub release download.** There is no published release
  (`gh release list` returns nothing), so the file was served from the host
  over HTTP. The Mark of the Web it arrived with is identical, so the Windows
  prompts are the same; the reputation SmartScreen assigns to a real release
  URL may not be.
- **Whether Defect 5 is a real fault.**

## Appendix — reproducing the two file lists

The inventory script is `inv.ps1`, run in the guest and copied back:

```powershell
# top level of both roots, then the trees that matter, then the registry
Get-ChildItem -LiteralPath $env:APPDATA   -Force
Get-ChildItem -LiteralPath $env:LOCALAPPDATA -Force
foreach ($p in @("$env:LOCALAPPDATA/DR Companion",
                 "$env:LOCALAPPDATA/DR Companion Data",
                 "$env:APPDATA/DR Companion")) {
  if (Test-Path -LiteralPath $p) {
    $f = @(Get-ChildItem -LiteralPath $p -Recurse -Force | Where-Object { -not $_.PSIsContainer })
    "$p : files=" + $f.Count + " bytes=" + (($f | Measure-Object Length -Sum).Sum)
  } else { "$p : absent" }
}
Get-ChildItem "HKCU:/Software/Microsoft/Windows/CurrentVersion/Uninstall" |
  ForEach-Object { (Get-ItemProperty $_.PSPath).DisplayName } |
  Where-Object { $_ -like "*Companion*" }
```

Run it against a machine where the app **is** installed and it must print the
`DR Companion` tree with a non-zero file count and the registry entry; run it
after an uninstall and both must be gone while
`io.github.dancockrell.dr-companion` remains. If it prints nothing at all in
either state, the script did not run — that is not a clean machine.
