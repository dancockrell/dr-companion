# Live play session — Phemius, 9 Sep 2026

The first real sign-in of a live DragonRealms character against this client.
Dan signed in as Phemius and handed the client over. Everything below was done
through the app's own controls over CDP (port 9350) against the running build
in `wt-live`, except where a row says otherwise.

Nothing here is a stand-in. Where a check could not be made, it says so rather
than guessing — see the COULD-NOT-CHECK rows, which are the honest half of this
document and the ones worth re-running.

## Headline

Twenty things tried. **11 worked, 6 broken, 3 could not be checked**, and one
turned out not to be a bug at all after being measured.

The session's main question — *why did signing in leave a three-version-old
bridge running?* — has a one-sentence answer with a fix in this PR: **nothing
in the app has ever refreshed the bridge script it tells Lich to run.**

## The bridge version, start to finish

### What the player met

The Game log's opening lines, verbatim from the running app:

```
10:32:13 PM Companion started.
10:32:13 PM Live bridge: connecting
10:32:13 PM Live bridge: connected
10:32:13 PM Bridge v0.11.0 on Lich 5.20.1, protocol 1
10:32:13 PM The bridge script running in Lich is v0.11.0, but this app ships
            v0.14.0. Reinstall it from Setup, then start the bridge again.
10:32:13 PM Loaded settings for Phemius on Prime.
```

and the character panel read **"This bridge does not report base stats yet."**

### Cause, established on disk

```
$ ls -l /c/Ruby4Lich5/Lich5/scripts/companion_bridge.lic
-rw-r--r-- 1 Admin 123457 Aug 29 20:18 companion_bridge.lic
$ grep -n "BRIDGE_VERSION = " /c/Ruby4Lich5/Lich5/scripts/companion_bridge.lic
33:  BRIDGE_VERSION = '0.11.0'
$ grep -n "BRIDGE_VERSION = " lich-scripts/companion_bridge.lic
33:  BRIDGE_VERSION = '0.14.0'
```

The Lich the app started, from `Win32_Process`:

```
rubyw.exe  ProcessId 66164  CreationDate 9/9/2026 10:30:17 PM
  lich.rbw <sal> --headless=11024 --start-scripts=companion_bridge
```

So the app told Lich to start a script called `companion_bridge`, and the file
that name resolved to was eleven days and three versions old. Nothing in the
launch path had ever looked at it. `install_bridge_script` has exactly one
caller in the whole tree — a button in the first-run wizard — and the wizard
skips itself once a machine is working. A player who set the app up in August
and updated it in September launches an August bridge for ever.

**The missing base stats are exactly this and nothing else.** Read live out of
the store:

```
character.stats  →  undefined
character.skills →  50 entries, real ranks
```

`StatsPanel` distinguishes three states on purpose, and `undefined` is its
"an older bridge never sends this key" arm. It was telling the truth. The
0.11.0 bridge does not emit `stats`; 0.14.0 does.

### Repair, walked the way a player has to

| # | Step | Result |
|---|---|---|
| 1 | Settings (gear) | opened |
| 2 | Looked for anything called "Setup" | **not present** — the nearest control is "Ruby, Lich and your frontend → Check what is installed" |
| 3 | Pressed "Check what is installed" | Setup screen opened; bridge row read *"Installed, but not the copy this build ships - reinstall it"* — the content-hash check is correct and was right all along |
| 4 | Pressed "Install the bridge script" | app log: `10:41:57 PM Bridge script installed to C:\Ruby4Lich5\Lich5\scripts\companion_bridge.lic` |
| 5 | Verified by content, not by the message | `md5sum` of the installed file now equals the shipped file exactly, and `BRIDGE_VERSION = '0.14.0'` |
| 6 | `;companion_bridge stop` via the command bar, to restart the script | **no effect** — port 7415 still LISTENING under pid 66164, `versions.actualBridge` still `0.11.0` |

Step 5's file timestamp read `20:22` after an install performed at `22:41`,
which briefly looked like a second session writing the file. It is not:
Windows `std::fs::copy` uses `CopyFileEx`, which carries the *source's*
LastWriteTime across. The app's own log line is the evidence that the app did
it.

So the repair is possible and it is not discoverable, and it cannot be
finished from inside the client: the file is now current and **the running
bridge is still 0.11.0**, because restarting the script needs a Lich restart
and the client offers no way to do either.

### The fix in this PR

`refresh_bridge_script()` in `src-tauri/src/setup.rs`, called from
`refresh_bridge_before_launch()` on **both** routes to a launched Lich
(`launch_lich_using` for sign-in, `launch_lich` for the launcher button),
immediately before the spawn.

- It reuses `copy_bridge_to_lich` and the existing CRLF-normalised content
  hash rather than adding a second way to install or a second way to compare.
- Three states, not two: `Updated` / `AlreadyCurrent` / `CouldNotCheck`. The
  last one is printed rather than swallowed, because that is the arm where the
  app is about to start a script it could not identify.
- It never blocks a launch. Refusing to sign a player in because a file copy
  failed is a worse client than a stale bridge.
- It takes no `AppHandle`. Threading Tauri's runtime type into `lich.rs`
  links the webview into the unit-test binary, which then fails to start at
  all with `STATUS_ENTRYPOINT_NOT_FOUND` — measured, not guessed. The bundled
  path is resolved once in the Tauri `setup` hook into a `OnceLock`, the same
  shape this crate already uses for `SPAWNED_LICH`.

Four tests in `bridge_staleness_tests`, and they are constrained from both
directions — sabotaging the decision function each way turns exactly the
intended pair red and nothing else:

| sabotage | red | green |
|---|---|---|
| never refresh | `a_stale_installed_script_needs_refreshing`, `an_absent_script_needs_installing` | the other nine |
| always refresh | `a_current_script_is_left_alone`, `line_endings_alone_do_not_trigger_a_refresh` | the other nine |

The sabotage harness aborts loudly if its anchor fails to match, and verifies
the restore is byte-identical. Its first version *did* fail to match — a
literal `\n` anchor against a CRLF working tree — and printed a green run that
proved nothing. That is recorded here because the green run looked exactly
like success.

One existing test was changed: `launch_lich_takes_no_character` asserted its
property through an exact fn-pointer type. The property ("no character name
can be passed to this route") is untouched and still enforced; only the
mechanism moved, and in the end the signature did not change at all.

### #8 is the interesting non-bug

The brief described the Combat panel's skill list as "all zeros", and it is —
but the panel is `MindstateBoard`, it shows **mindstate**, and mindstate is
genuinely `0` for all 50 skills because the character is standing in a town
doing nothing. The bridge is sending real ranks the whole time.

Reporting it as a data bug would have been wrong. What is defensible is that
50 rows of `0` with no heading and no rank anywhere on the face is
indistinguishable, to a player, from a panel that is broken — the rank is only
in the `title` tooltip. Filed rather than fixed, because the board's design is
deliberate and argued in its own header, and changing it is its owner's call.

### #19, said honestly

The command bar accepted `look`, `time`, `inventory` and
`;companion_bridge stop`, and cleared itself each time. That clearing is not
cosmetic — `GameCommandBar.send()` only reaches `setCommand('')` after
`await sendGame(outgoing, 'player')` resolves, and the code says so: *"A line
disappearing is the player's receipt that native accepted it."* So the lane
accepted every command.

No response to any of them was observed. `inventory` left the Inventory stream
frozen at its sign-in contents (15 rows, last line 10:31 PM) across six
seconds, using real trusted keystrokes rather than synthetic events.

This is reported as could-not-check, not as broken, for three reasons:

1. Lich's debug log records the launch and not the command traffic, so the
   independent instrument that would settle it does not exist on this machine.
2. `;companion_bridge stop` failing is consistent with the app writing to the
   detachable-client socket in a way Lich does not treat as a script command,
   which is a different defect from "commands do not arrive".
3. **The character was being driven by someone else during the test.** He
   walked Empaths' Guild → Flamethorn Way → Magen Road → Trothfang Street
   while I sent nothing that moves. I stopped sending game commands at that
   point rather than inject into a character another actor was steering, so
   the run is incomplete by choice.

Anyone re-running this should do it on a character nobody else is driving, and
watch the socket rather than the panes.

reproducing step and the live evidence:

Related, and read before writing any of this so as not to compete with it:
**#534** (the bridge gave up before `companion_bridge` bound its port and

`src-tauri` only, and no in-flight branch modifies `lich.rs`, `setup.rs` or
`lib.rs`.

## What was not disturbed

- No irreversible or costly action: nothing dropped, given, sold, bought,
  stored, junked; no money moved; no combat; no travel out of a safe town; no
  other session's scripts stopped; the character was never quit.
- No credential field was touched or read.
- The only write outside this worktree was the bridge script the app itself
  installed into Lich's scripts folder, through the app's own button, verified
  by hash afterwards.
- Lich (pid 66164) left running.
