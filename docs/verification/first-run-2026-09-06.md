## How this run was driven

`/S` for the DR Companion installer, and the app's own UI for everything else.
E2's seven prompts are not under test here — they were measured on 5 September
and nothing in these six PRs touches the NSIS pages — so the installer ran
silently and the app was launched from the script, which is what
`docs/verification/uninstall-2026-09-06.md` established as equivalent for
everything except the SmartScreen chain.

`tools/vm-shot.ps1` is committed with this document. It captures the screen from
**inside** the guest (`CopyFromScreen` after `SetProcessDPIAware`), lists every
visible top-level window with its `GetWindowRect`, and clicks and scrolls by
coordinate. It exists rather than `VBoxManage controlvm screenshotpng` because
that returns a stale framebuffer on this VM, and a stale frame and an empty
desktop are indistinguishable. It prints its denominators: the captured size,
`WIN listed N of M top-level windows enumerated`, and the PNG's byte count, and
it throws if `EnumWindows` returns nothing or the PNG is under 5 KB — a listing
that enumerated nothing is not evidence that nothing was there.

Two of its own bugs were caught by those denominators rather than by reading it,
and both are the shape this project keeps meeting: `Write-Output` from inside an
`EnumWindows` callback goes nowhere, so the first run printed
`WIN listed 2 of 89` and not one `WIN` line; and `GetWindowTextW` marshalled as
ANSI gave every window a one-character title (`WIN 'D' proc=dr-companion`). Both
would have read as "the app has no window" to anybody skimming.

# New defects

## New defect 1 — the clamp measures the client area, so the window still hangs 15 px into the taskbar

`window_size::clamp_to_work_area` fits the window inside the work area less a
24 px margin, and `lib.rs` then applies its result with `window.set_size`, which
on Tauri sets the **inner** size, and `window.set_position`, which sets the
**outer** position. The frame is 16 px wider and 39 px taller than its content,
so the bottom edge lands `39 - 24 = 15` px past the bottom of the work area.
Measured on both screens, and the arithmetic is the same either way:

| screen | work area | placed at | outer rect | bottom vs work area |
|---|---|---|---|---|
| 1024x768 | 1024x720 | (24, 24) | `W=992 H=711` | 735 vs 720 — **15 px over** |
| 1440x900 | 1440x852 | (130, 24) | `W=1196 H=843` | 867 vs 852 — **15 px over** |

Nothing important is lost — the app's own bottom bar is inside the window, not at
its edge — but it is 15 px of window behind the taskbar on every screen, and it
is one line to fix: clamp against the frame size, or set the outer size.
Shots 01 and 02 carry the measurements.

**Fixed in PR #427; not yet re-measured on the VM.** Issue #417.
`clamp_to_work_area` takes the frame as an argument now, fits and centres the
**outer** rectangle inside the work area less the margin, and subtracts the
frame again for the content size handed to `set_size`. Both rows above are
`window_size.rs` cases, using the VM's own 16x39, each asserting that the outer
rectangle is inside the work area less its 24 px margin: 696 rather than 735,
and 828 rather than 867.

The frame is read from the window (`outer_size()` less `inner_size()`) rather
than assumed, because it is not a constant. Measured once on the development
machine, at scale 1.25: `outer 668x1022` against `inner 650x975`, which is
18x47 physical and **14.4 x 37.6 logical**, where this VM measured 16x39. A
hardcoded 15 px would have been wrong on both.

What is checked and what is not: the arithmetic is tested, and the frame
measurement above was taken from the real running app. The window itself has
**not** been re-measured on a 1024x768 display, because the development machine
cannot produce one. The check that would settle it is the one that found this
defect, and it is still owed on the next clean-VM run:

```
# from inside the guest, with the app running
GetWindowRect on the 'DR Companion' window, against SPI_GETWORKAREA;
the outer bottom must be at or above the work area's bottom less 24.
```

## New defect 2 — the empty state does not fit the default window and does not scroll

`WaitingForCharacter` is taller than the app's own default window, and its
container clips it at both ends instead of scrolling. On the default 1180x820
window it is cut off **above** the heading and **below** the buttons, so a
first-time user sees the middle of an explanation, cannot read "Nothing is
connected yet.", and **cannot reach "Start the demo" or "Connection help" at
all**. The mouse wheel does nothing over it, `{HOME}` does nothing, and there is
no scrollbar.

Reproduced at three sizes, twice, on two separate installs of the same build:

| window | content height | the empty state |
|---|---|---|
| 1440x900, app default (shot 11, 21) | 820 | clipped top and bottom; buttons unreachable |
| 1440x900, maximised (shot 12) | 852 | clipped top and bottom; buttons unreachable |
| 1600x1200, maximised (shot 13) | 1104 | whole panel visible, buttons present |

Shot 13 beside shot 12 is the evidence that nothing is missing from the build —
the buttons exist and render, they are simply outside a box that will not scroll.
A person on a 1366x768 or 1920x1080 laptop, which is most people, gets the
clipped version, and the only route into the demo #386 built is off-screen.

This is also why Defect 3's demo checks in this document were done at 1600x1200:
at any smaller size the button could not be pressed.

### Fixed in PR #428

Two changes, because either one alone leaves a hole. The two actions and the
help link now sit directly under the heading instead of under six paragraphs, a
command block and the Lich launcher, so they are above the fold at every size
the window is allowed to be. And the container is `overflow-y-auto` rather than
`overflow-hidden`, so nothing is unreachable whatever the panel grows into
later. `justify-center` was removed as part of the second: a flex column that
centres content taller than itself pushes the overflow off the **top** as well,
where no scrollbar can reach it, which is why the heading was missing in shots
11, 12 and 21 and not only the buttons.

Nothing was deleted to make it fit. The explanation is the same length and now
reads in a better order, and it is asserted still reachable - the check below
includes the last prose paragraph precisely so a pass cannot be earned by
shortening the panel.

Measured in a real browser at four window sizes, before and after, with
`node tools/empty-state-measure.mjs http://127.0.0.1:5191/ <label>` against a
dev server on that port. Each control is found by the words a person reads, and
the question asked of it is whether a click would land on it
(`document.elementFromPoint` at its centre), then whether scrolling a box a
person can actually scroll would bring it there.

| window | before | after |
|---|---|---|
| 1180x820, the app default | all visible in Chrome (see the limit below) | all visible; buttons at y=273 rather than y=514 |
| 992x711, a 1024x768 screen clamped | all visible in Chrome | all visible; buttons at y=218 rather than y=459 |
| 720x480, the declared minimum | all visible in Chrome | all visible; buttons at y=104 rather than y=344 |
| 720x300, forced overflow | heading and attach line off the top, **UNREACHABLE**; both buttons and the last paragraph clipped by `main`, **UNREACHABLE**; container `overflow-y: hidden`, 284/216 | heading, attach line and both buttons visible; last paragraph reachable by scrolling; container `overflow-y: auto`, 399/216 |

Screenshots at 992x711: `empty-state-2026-09-06-before.png` and
`empty-state-2026-09-06-after.png`.

**The limit of the stand-in, and it is a large one.** These measurements were
taken in headless Chrome against the Vite dev server, not in the app. Chrome is
not WebView2 and `isTauri()` is false there, so `LichLauncher` - roughly 350 px
of the real panel, and the whole reason it overflows at 1180x820 - renders
nothing. That is why the browser reported the first three rows as fine in the
**before** column while the clean VM's own screenshots plainly show the defect:
the stand-in cannot reach the height the app is at. The fourth row is in the
list for that reason alone. It is shorter than the app's declared minimum and
exists to force, in Chrome, the overflow condition the real app is in at every
size, so the scrolling path is exercised rather than assumed. A run on the VM
against the real WebView2 is still the thing that would close this properly.

The regression check is `tools/first-screen-shots.mjs` section e, which sweeps
the same four sizes and asserts by measurement rather than by class name, plus
two source checks in `tools/first-screen-test.mjs` section 6 (the container
declares vertical overflow auto, and does not centre content it may be too
small to hold). Sabotage: putting `justify-center overflow-hidden` back on the
container and returning the buttons to below the launcher turned 6 checks red
in the shots harness - naming the size, each control and its rect - and 2 red
in the source check. The file was restored by md5.

## New defect 3 — a popped-out panel window renders blank white

`MapPanel`'s "Open in its own window" control opens a real window —
`WIN 'DR Companion — Map' proc=dr-companion pid=3532 L=26 T=26 R=802 B=705
W=776 H=679` — whose contents never paint. White, not the app's dark surface,
which says the document never rendered rather than that a panel came up empty.

Measured twice, on two independent installs and two separate app launches:
20 s and 80 s after opening, including a click into the window to give it focus
(shots 15, 22). Nothing appeared in the main window's Console in the meantime.

The cause was **not established** — the map database was not installed on this
machine, so a crash in the map panel with no boundary above it is a candidate and
nothing more. What is established is what a first-time user gets: an empty white
window, and no demo banner in it, which is the state PR #409 exists to prevent.

**Fixed in PR #431 — cause: `open_panel_window` was a synchronous
`#[tauri::command]`.** A synchronous command runs on the main thread, which is
the event loop's thread; `WebviewWindowBuilder::build()` dispatches the creation
onto that loop and then blocks waiting for the answer, so the loop can never
deliver it. The map database was innocent: the panel never ran at all.

Established rather than reasoned, on a release build of `main` driven over CDP
(`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`):

- the pop-out webview's document was **`about:blank`** — `location.href`
  `"about:blank"`, `document.documentElement.outerHTML.length` 39, no `#root`,
  `styleSheets.length` 0, computed body background `rgba(0, 0, 0, 0)`. That is
  the white: not a panel that came up empty, a document that was never fetched;
- `Page.enable` + `Network.enable` on it recorded **no navigation of any kind**
  in twelve seconds, so no request for `index.html?view=panel&id=map` was ever
  issued;
- `window.__TAURI_INTERNALS__.invoke('open_panel_window', …)` was still
  **pending after 67 s** (sampled at 2, 5, 10, 20 and 30 s), while the main
  window kept answering `Runtime.evaluate` throughout — so the block was in the
  Rust command, not in the webview;
- a `std::fs::write` placed immediately after `.build()` in a temporary build
  **never ran**, which is what puts the block inside `build()` rather than
  anywhere else in the command.

The fix is `async fn` on `open_panel_window` (and on `close_panel_window`, which
dispatches `close()` the same way). With it, the same invoke resolves inside two
seconds and the pop-out loads
`http://tauri.localhost/index.html?view=panel&id=map`: dark surface
(`rgb(13, 12, 10)`), one stylesheet, a mounted React tree, the map panel's own
text. `docs/verification/popout-2026-09-06.png` is that window.

`tools/window-command-async-test.mjs` asserts the class rather than the
instance: every `#[tauri::command]` in `src-tauri/src` whose body constructs a
window builder must be `async`, with both lists derived from the source and a
floor on the number of commands parsed so a broken parser cannot report a clean
run.

Not checked in *this* run: **#409's compact demo banner in a pop-out.** The
pop-out opened and rendered, and here it showed the map panel's "No bridge"
state rather than the demo. So Defect 3's pop-out half stopped being
COULD-NOT-CHECK-because-blank and became an ordinary unchecked item.

**Checked since, and it comes up in the demo.**
`docs/verification/popout-mode-2026-09-06.md` is that measurement, on a release
build driven over CDP with two real webviews of one process. Main window taken
into the demo by its own **Start the demo** button, then
`open_panel_window('map')`:


If either script prints nothing, it did not run — that is not a clean machine.

Three mechanics this run learned that `docs/verification/vm.md` and
`uninstall-2026-09-06.md` do not have:

- **`guestcontrol run --wait-stdout` comes back empty when the guest script
  launches a GUI process.** Not truncated: empty, with a zero exit. Have the
  guest script redirect itself to a file, delete that file in the guest first,
  poll for it, and require a marker the script itself writes as its last line.
- **PowerShell writes that file UTF-16, and `grep` treats it as binary and
  matches nothing.** `tr -d '\000'` before matching, or every assertion on the
  output silently passes over an empty string — a check that cannot fail.
- **`VBoxManage guestcontrol run` segfaults on this host having started
  nothing.** Retrying is safe only if the guest script is idempotent; anything
  that starts an installer needs its own sentinel file, and this run used one for
  each of the three irreversible steps.

Where this document and those scripts disagree, **the scripts are right and the
prose is stale.**
