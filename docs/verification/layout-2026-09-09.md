# The play-first frame, measured before and after

9 September 2026. Dan, after his first live session, in two messages:

> its really hard to run. the godot screen should include the map and the
> ability to easily put it into mini map mode or pop it out into a big map,
> nice interface. we had a lot of the map built although we definitely update
> what we were doing before. I'm not sure about all the menus but the game
> screen needs to be quite large so that I can actually play the game as mud.

> it's not best to put the screen in the middle... put it in the right corner
> and have a bottom bar of icons for various functions and then on the left you
> have room for your text heavy windows.

That is an argument about area, so it is settled with area rather than with an
opinion about a screenshot.

## How these numbers were taken

`node tools/layout-regions.mjs <url> <before|after>` drives a real browser
(`tools/browser.mjs`), clicks "Start the demo" the way a person does, resizes
to each window size and measures every named region's rectangle. Each region is
reported **measured**, **hidden** or **absent** - a region this build does not
have and a region rendered at zero size mean opposite things, and collapsing
them into "0 px" would make the two rows below that say "absent" unreadable.

"Before" is `origin/main` at c9b904f6 plus one inert `aria-label` on
`StatsPanel`'s root, so the vitals could be measured as themselves rather than
as the rail that also holds Risk. It changes no layout.

## The finding

At Dan's own window the game text held **17.9%** of the screen in a 223px strip
along the bottom, while the room picture in the middle held **38.8%**. That is
the wrong way round for a MUD, and it is what "really hard to run" was about.

## Characters per line

Measured rather than computed: the real advance of a real sentence in the
transcript's own computed font, and the region's usable width divided by it.

| size | before | after | type |
|---|---|---|---|
| 1997x935 | 217 | 216 | 16px / 24px line height |
| 1180x820 | 127 | 127 | 16px / 24px |
| 1366x768 | 147 | 147 | 16px / 24px |

Unchanged, because the transcript was already full-width in the console row -
what changed is its height, from 223px to between 496 and 663. **216 characters
per line is wide for continuous prose** (50 to 100 is the usual advice) and
it is left as a question below rather than fixed here.

## Readability

- Type: 16px with a 24px line height, unchanged.
- The scrollback still sticks to the bottom while it is at the bottom, and now
  offers a **Latest** control while it is not - a floating pill in the bottom
  right of the scroll box that appears only when scrolled up, so it is never
  furniture. Changing channel counts as being at the bottom again.
- The command line is inside the viewport and clickable at every size in the
  suite, asserted with `elementFromPoint` rather than with a rectangle.
- The command line now regains focus after a send that **worked**, not only
  after one that failed. Pressing Enter left focus in the box by itself;
  pressing the Send button did not, and the next thing typed went nowhere.

## The three regions as built

- **Left, the text.** `GameChatColumn` - the scrollback, the channel tabs, the
  connection bar and the command line - as `flex-1`. It is `fitColumns`' "room"
  slot, which is the slot that absorbs width nobody claimed and whose
  `ROOM_MIN` floor was written for exactly this content.
- **Right corner, the scene pane.** The first thing in the right rail, so it
  sits in the workspace's top right corner. Three states: `minimap`, `popped`,
  `hidden`. Under it, in the same rail: vitals, risk, the experience strip
  ("all the way to the right", where Dan put it) and the local AI worker's
  status.
- **Bottom, the icon bar.** One control for the scene pane's three states, then
  one icon per panel.

## The scene pane's three states

| state | what it does | what the rail asks for |
|---|---|---|
| `minimap` | drawn in the top right corner, beside the text | the stored width (380 default) |
| `popped` | opened in a window of its own through the existing panel-window machinery (the new `board` panel id); the corner says where it went | capped at 250 |
| `hidden` | not drawn; the width goes back to the text | capped at 250 |

One control cycles them, in the bar, naming the state it will move to. The cap
is a display-time ceiling, not a rewrite - the stored width comes back the
moment the pane does. The state is stored **per class of window size**
(`narrow`/`standard`/`wide` by width, `short`/`tall` by height, all cut at
`columns.ts`' own frame minimums), because it is a different decision at each
size and a single stored answer makes one of them wrong.

Name from `PANEL_TITLES`, description from `PANEL_DATA_CONTRACTS[id].purpose`.
No third table.

| scene | (the pane itself) | three states, one control | whenever the window changes shape |
| tasks | Tasks and scripts | the icon grid of every Python/TypeScript/Ruby entry, what is running, the pinned hotbar | often, and it was in the console row |
| actions | Actions | the twelve macros sent by hand between starting and stopping | often |
| inventory | Inventory | worn and carried items, containers, burden | often |
| mindstate | Mindstate | every skill and how close each is to locking | often; also permanently on screen in the rail |
| training | Training | what the character is actively trying to raise | daily |
| room | Battle | the paperdoll beside the enemy cards | in a fight |
| stats | Stats | base stats and derived numbers | rarely |
| launcher | Activities | quick-start entry points | rarely |
| scripts | Script Library | browsing what exists, offline included | rarely |
| game | Game | the room, the text and the command line as one panel, for a second monitor | rarely |

| config | Player config | highlights, aliases, macros, substitutes, gags, presets, variables | occasionally |

### Cut, with the reason

- **`vitals` as a bar entry.** `PANEL_CONTENT.vitals` renders `null` - there is
  nothing behind that id to open, so a bar icon for it would be a control with
  no live target. The vitals themselves are on screen permanently in the rail.
- **`risk` as a bar entry.** Permanently on screen in the rail, directly under
  the vitals. A bar icon would be a second way to reach something already
  visible.

Both are recorded in `OFF_BAR` in `src/lib/panelBar.ts` with those reasons, and
`tools/play-first-layout-test.mjs` asserts that every panel is either on the bar
or named there - so a panel that quietly stops being reachable fails a check
rather than disappearing.

### Left as questions, with the evidence

1. **216 characters per line at 1997x935.** The transcript is now tall as well
   as wide, and continuous prose that wide is hard to track from the end of one
   line to the start of the next. A max width would leave dead space, which is
   the sort of thing this project has an explicit rule against; a second column
   of text is a bigger decision than this change. Not touched. The numbers are
   in the table above.
2. **The `game` panel on the bar.** It opens the room, the transcript and the
   command line in a window of its own, which is now nearly what the main
   window already is. It is kept because a second monitor is a real use, and
   because removing a route is not something to do on a guess. Worth Dan's
   opinion.
3. **The Actions panel moved off screen into the bar.** The twelve macros were
   a permanent 250px column. `BattleActionBar` inside the scene pane still
   carries the combat deck, and the hotbar and Stop/Pause are permanently on
   screen in the footer, so nothing about starting or stopping moved. Whether
   the twelve macros deserve to be permanently visible is a judgement about how
   Dan plays.
4. **`AiWorkerPanel` stayed in the rail** rather than moving to the bar, on the
   grounds that a background worker whose status only exists while something is
   open reports it to nobody - which is the exact reason it left Settings. It
   is the least-watched thing in the rail and could go.

### Sabotage, run 9 September 2026

Control first: the suite is green before anything is broken (exit 0, 0 red).
A run that fails for its own reasons satisfies "exit non-zero" exactly as well
as a caught sabotage does.

| sabotage | result |
|---|---|
| `SCENE_RAIL_W` 380 -> 1400 | exit 1, 3 red, all `the game text holds most of the width`, first naming `1180x820`; restored, md5 `96dd22e8` -> `96dd22e8` |
| the text region given `order-last`, so the pane leaves the corner | exit 1, 3 red, all `the scene pane is in the right corner, not the middle`, first naming `1180x820`; restored, md5 `900a0ed2` -> `900a0ed2` |
| `inventory` dropped from `PANEL_BAR_ORDER` without being named in `OFF_BAR` | exit 1, 6 red, naming both the source manifest check and the rendered-bar check; restored, md5 `f1d8be61` -> `f1d8be61` |
| `sizeBucket` returns one bucket for every size | exit 1, 1 red: `a different size keeps its own answer rather than inheriting that one`; restored, md5 `96dd22e8` -> `96dd22e8` |
| the bar's tooltip reduced to the bare name | exit 1, 5 red, all `and what it is for, on hover and on focus`, first naming `720x480`; restored, md5 `b5c6aa52` -> `b5c6aa52` |

The third case is the one worth reading. It first reddened **one** check where
two were expected, because the bar's count was compared against
`PANEL_BAR_ORDER` and both move together - dropping a panel from the order
satisfied that comparison perfectly while making the panel unreachable. The
suite now also compares the **rendered** bar against the panel manifest, and
the sabotage reddens both. That is what asserting *which* checks go red is for;
asserting only that something went red would have missed it.

## What this cannot tell you

Chrome is not the app. `isTauri()` is false under the dev server, so
`openPanelWindow` no-ops: the `popped` state, the rail's response to it and the
note saying where the pane went are all exercised, and the window itself is
not. That half needs the packaged app or `tools/mud-client-e2e.mjs`.
