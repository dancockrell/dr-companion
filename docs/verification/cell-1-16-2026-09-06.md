# Cell 1-16 drew no block — 6 September 2026

Issue #376, from a loose end left open by
[`token-height-2026-09-06.md`](token-height-2026-09-06.md): cell `1-16`, a 3 m
`interior-cutaway` carrying four unregistered primitive kinds, "draws no
placeholder block at all at Route distance", while every other cell that should
draw one does.

## The finding is not the one the report expected, and it is bigger

`ContentRegistry` was never the problem. Fed `1-16`'s real entry it returns five
nodes — the registered `interior-floor-5m` factory's plane and **four
placeholder blocks at 4.40 × 3.00 × 4.40 m**, the footprint that cell publishes.
Measured before any change was made, by building the cell out of the tree the
way `content_registry_test.gd` does. So the three candidates the report named —
an unregistered kind short-circuiting to nothing, a kind-count branch, a
distance tier skipping placeholders — are all refuted, and none of them exists
in that file.

The line is **`godot/scripts/cell_visibility_policy.gd:29`**:

```gdscript
var target_id := String(exit.get("targetCellId", ""))
```

A null `targetCellId` is the manifest's documented way of saying an exit leads
out of the loaded subset. `world_manifest_loader.gd` calls the null "the whole
signal, in both the mock fixture and a live snapshot", and
`tools/godot-fixture-contract-test.mjs` already asserts, over both subjects,
that they carry some — the mock fixture has 13 of them across 9 cells, and the
live compiler emits them too. Every other reader of that field uses `str()`,
which tolerates a null. This one used `String()`, which has no constructor
taking Nil, so it raised at runtime and abandoned the breadth-first walk.

What that cost was not one skipped exit. `detail_window()` returned null,
`world_root.gd:_apply_detail_window()` got no ids, and **no cell anywhere on the
board mounted any content at all** — no blocks, no ground, no props. `1-16` was
simply the room the capture was pointed at; its fixture tokens still drew,
because they come from `entity_projection_layer.gd`, which parents to the cell
holder rather than to its detail content, and that is why the emptiness read as
"this one cell has no block" rather than as "nothing is being drawn".

It depended entirely on which room the player stood in, which is why nobody had
seen it: the walk only reaches such an exit inside `DEFAULT_DETAIL_HOPS`. From
`1-14` — the mock board's starting room and the origin of every capture in this
directory before this one — it never does, and the board draws. From `1-16`, one
hop from `1-40` and its three null-targeted exits, it does. With the defect
present, **4 of the mock's 19 cells are usable origins and 15 are not.**

Camera distance is not in this at all. `detail_window()` takes no camera
argument and `_apply_detail_window()` runs on every snapshot regardless of mode;
Route distance is where it was seen, not what caused it.

## A second instance of the same contract, found in the same pass

`bridge_client.gd:211` read the same nullable field as
`var target_id: String = exit.get("targetCellId", "")`. Assigning Nil to a typed
`String` raises too — measured, in a three-line script: *"Trying to assign value
of type 'Nil' to a variable of type 'String'"*, and the function is abandoned.
The two lines immediately below it exist to reject exactly this case
(`"exit's destination is outside the loaded manifest"`) and could never run, so
walking one of the mock board's thirteen null-targeted exits produced no
snapshot, no rejection and no signal at all. Fixed on the same path.

## The fix

| | |
|---|---|
| `godot/scripts/cell_visibility_policy.gd` | a non-`String` target is skipped, which is what "outside the loaded subset" means. A type test rather than `str()`, so no `"<null>"` can be smuggled into the id comparison below it |
| `godot/scripts/bridge_client.gd` | the same, keeping the rejection it already had reachable |
| `godot/scripts/world_root.gd` | a loaded cell is always at distance 0 from itself, so an empty window for one is the policy having *failed*, not a small budget. It now says so with `push_error` naming the cell. An empty window for a cell not in the manifest is the honest answer and is untouched |

The third is the one that would have made this visible on the day it landed:
before it, the entire board drawing nothing produced one console line about a
String constructor and nothing else.

## Tests

`godot/tests/cell_detail_window_test.gd`, 26 checks. The property it asserts is
not "1-16 draws a block":

- **N of N: every one of the 19 loaded cells is a detail-window origin whose
  window at least contains itself.** This is the chooser with the wrong answer
  available — from `1-14` the walk passes with the defect present, so only
  sweeping every origin separates a fix from a coincidence. `1-14` is kept as a
  named control so the sweep cannot pass by being a blanket change.
- The fixture really does carry the shape the rule turns on: 13 non-string
  targets across 9 cells, floored at 3, and `1-40` named among them.
- No id in a window is absent from the manifest, so no null became an id.
- **Counts of drawn things, not "no error"**: mounting `1-16` the way
  `world_root.gd:_mount_cell_detail` does draws 5 nodes for 5 primitives, 4 of
  them placeholder blocks, 0 of them off-size against the footprint that cell
  published, and the 1 registered kind still draws its own mesh.
- Synthetic cells where the wrong answer is available: four unregistered kinds
  on a cell whose footprint is 7.5 × 6.25 × 2.25 (sizes no board publishes) draw
  four blocks at exactly that; one registered kind draws its mesh and no block;
  a cell with no primitives draws 0, and that 0 is compared against the 4 above
  so the counts cannot be whatever the mounter always returns.

`MIN_EXPECTED_CHECKS := 20` against a real 26, because a GDScript runtime error
does not stop `_initialize` reaching the summary — which is the failure mode of
the bug under test.

| | before | after |
|---|---|---|
| `node tools/godot-tests.mjs` | 14 scripts, 218 checks | **15 scripts, 244 checks**, all passed |
| `node tools/run-tests.mjs` | no failures | no failures |

### The contract test is left alone, deliberately

The rule the brief asked about — "a cell with kinds none of which the registry
admits" — is a **viewer-only property** and would have caught nothing here. Which
kinds are admitted lives in `shared_asset_content.gd`, not in the manifest, so
the fixture cannot state it; and such a cell is not a defect anyway, it draws
all placeholders, which is the honest degraded state. The fixture property that
actually matters to this bug — that both subjects carry null-targeted exits — is
already asserted N-of-N with a floor by
`tools/godot-fixture-contract-test.mjs` ("carries the null-targeted exits the
rule turns on"). Adding a rule there would have been a second opinion about a
fact it already states.

## Sabotage

`String()` put back on that one line, by regex rather than a typed copy so a
sabotage that stops matching aborts instead of reading as a pass, restored from
a byte copy and verified by md5:

```
cell_visibility_policy.gd md5 before    = c2f011ee2753a39bb70f1c62c243e086
clean  : 26 checked, 0 failed, verdict "all passed"
cell_visibility_policy.gd md5 sabotaged = 1b5152d68aebc70c65125c99b71b15ba
sabotage: 26 checked, 4 failed, verdict "FAILED"
    FAIL every loaded cell is a detail-window origin that at least contains itself  4 of 19 cells; first failure 1-12 -> {  }
    FAIL the reported cell's window contains the reported cell  0 ids
    FAIL and reaches the null-targeting neighbour that used to abort the walk  []
    FAIL and it is not one lonely id, which is what an aborted walk returns  0 ids
cell_visibility_policy.gd md5 after restore = c2f011ee2753a39bb70f1c62c243e086
restored: 26 checked, 0 failed, verdict "all passed"
```

The check count is identical across all three runs. A red from a script that
failed to parse would have asserted fewer, and the harness refuses that case
rather than reading it as a catch. It also refuses to interpret anything if the
clean run is not green first.

## What is not settled

- **One origin, one camera distance.** The picture is `1-16` at the viewer's
  default. The 19-of-19 origin sweep is asserted in the Godot test, not in
  captures.
- **The live compiler emits null-targeted exits too**, so this was not a mock
  fixture curiosity: any real room within two hops of one that leaves the loaded
  zone drew an empty board. That is asserted by the contract test's live subject
  and has not been photographed against a real Lich session.
- **`bridge_client.gd:211` is fixed but is not covered by a new test.** It is
  mock-mode movement through a null-targeted exit; the rejection path below it
  is now reachable, and that it raised was measured directly rather than in the
  suite.
